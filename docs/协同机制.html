UESTC-Rescue 协同机制

协同不是一种机制，是四层叠起来的。下面从最底层往上排，越往上越"显式"。

四层协同
底层

分区：先决定"谁负责哪一片"

靠聚类算法把地图切成几块，每个小队认领一块。没有这一层，所有单位会往同一个热点挤。
对应代码：MergeGroupings（动态聚类）、CentroidDivisionSystem（分割）、NeighborBuildingSearch（建筑邻接）。

第二层

信息共享：把自己看到的讲出来

每个单位把"我看到的东西"编成标准报文广播出去。这是最基础也最容易失效的一层。
对应代码：UESTCPacketDispatcher（按带宽择优选信道发出去）、UESTCBandListener（决定听哪些频道）。

第三层

集中指挥：指挥中心拍板"谁去哪"

指挥中心汇总全局信息，算出"单位 → 目标"的映射表，再编成命令发给对应小队。
对应代码：PatrolTaskDelegator / UESTCDispatcher 算映射表 → PickerDispatcher 编成 CommandFire / CommandPolice / CommandAmbulance 发出。
注意：只有在有指挥中心的地图（如 kobe）这一层才存在；kobe1 这种没有中心的地图，这一层直接不存在。

最上层

跨兵种专线：把话说到该听的人耳朵里

给三个兵种各开一条专用信道，用"报文类型白名单"过滤：本兵种的消息无条件放行，其他兵种的按需放行。
对应代码：BlazeRescueLink（消防）、MedicRescueLink（医疗）、RoadClearanceLink（警察）。

协同失效时的三个检查点（按顺序查）

① 电台真的通了吗

订阅频道数超上限 → 服务器只写日志，智能体毫无反馈，订阅全部作废。

agent X tried to subscribe to N channels
but only M allowed   ← 见到这行就是没通

② 报文有没有被带宽挤掉

每个频段的字节数是死的。优先级排得不好，关键报文会在发射前被整包丢掉。

bestInjectionSlot < 0 → break  ← 后面全丢

③ 中心到底有没有在指挥

对比 kobe（有中心）和 kobe1（无中心）的成绩。如果两张图分数差不多，说明第三层协同根本没起作用。

当前代码里这一层的已知问题

消防站分配器是坏的

config/module.cfg 指向的 UESTCFireCompanyAssignment 这个类不存在，消防指挥中心的分配功能实际上没接上。

警察搜索链也是坏的

UESTCExtActionClear 同样不存在，侦察警力的清障链路断开。

频道数推算有误

UESTCBandListener 用 频道总数 - 1 当成可用频段数，在 2 频道图上会算错。
